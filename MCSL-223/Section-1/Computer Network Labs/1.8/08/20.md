# 20. Start the TCP application at Time 1 second.

We need to ensure that your TCP application (the sender) begins its transmission at exactly 1.0 second in the simulation timeline.
​In NS-3, this is achieved by calling the Start() method on the ApplicationContainer. Starting the application at 1 second (rather than 0) allows the network's underlying protocols, such as routing and neighbor discovery, to stabilize before data begins to flow.


**​C++ Code Implementation**
​In your script for the dumbbell topology, locate the section where you define your TCP applications and apply the following timing:  

```c++```
```
// 1. Setup the TCP Server (Sink) on Node n2
// It is best practice to start the receiver slightly BEFORE the sender
uint16_t port = 8080;
PacketSinkHelper sink ("ns3::TcpSocketFactory", 
                         InetSocketAddress (Ipv4Address::GetAny (), port));
ApplicationContainer sinkApps = sink.Install (nodes.Get (1));
sinkApps.Start (Seconds (0.5)); // Sink starts at 0.5s
sinkApps.Stop (Seconds (20.0));

// 2. Setup the TCP Client (Source) on Node n1
BulkSendHelper source ("ns3::TcpSocketFactory", 
                         InetSocketAddress (interfaces.GetAddress (1), port));
source.SetAttribute ("MaxBytes", UintegerValue (0)); // Unlimited data

ApplicationContainer sourceApps = source.Install (nodes.Get (0));

// --- TASK 20: START THE TCP APPLICATION AT TIME 1 SECOND ---
sourceApps.Start (Seconds (1.0)); 
sourceApps.Stop (Seconds (20.0));

```

**Why Start at 1 Second?**
Sir, according to the logic of your lab manual and the MCS-218 textbook's discussion on protocol stability:
Routing Convergence: In complex topologies like the dumbbell, the GlobalRoutingHelper needs a small amount of time to populate the routing tables across all routers.
ARP Resolution: The very first packet in a simulation often triggers an ARP (Address Resolution Protocol) request to find the MAC address of the next hop. Starting at 1 second ensures these initial overheads don't interfere with your primary throughput measurements.
Experimental Baseline: In Session-8, we often start a TCP flow at 1.0s and then introduce a "competing" UDP flow at 5.0s. This 4-second gap allows us to see the "clean" TCP performance before the bottleneck link becomes congested.
Verification
When you run the simulation, you can verify this timing by looking at the terminal output or the .tr (trace) file. You will see that the first "Enqueue" or "Transmit" event for a packet with the TCP header appears at exactly +1.000000s.
